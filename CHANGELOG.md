# Changelog

All notable changes to this project will be documented in this file.
Format based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased] (targeting v0.2.0)

### Security
- `.emeralddb` backup import/export: IDs read from an imported backup file could reach a *later, unrelated* export unbound — they were concatenated directly into SQL `IN (...)` clauses instead of being passed as parameters. Because sqlx executes each `;`-separated statement in a string, a crafted backup could smuggle in arbitrary SQL that only ran the next time some other data was exported. All such lookups are now parameter-bound. (`src/lib/dbBackup.ts`)

### Added
- **A Home button at the top of the left rail**, above Journal, opening the dashboard. Until now the only way there was clicking the Emerald logo in the title bar — a logo in the window corner reads as decoration, not as a link, and as a button it also took dragging away from that corner. The logo is a plain image again.
- **The View menu can show and hide both sidebars.** Two ticked entries above *Reset View* — *Entry List* and *Properties*, named after what each sidebar holds, matching the rail buttons' own tooltips rather than inventing a second vocabulary for the same two toggles — on Windows/Linux in the app's own menu bar and on macOS in the native one (as real `CheckMenuItem`s, kept in sync by a new `set_view_menu_checked` command, since the rail's own toggle buttons can change the same state without the menu ever being opened). The tick follows whichever route was used. Until now the rail's two small toggle buttons were the only way to bring a closed sidebar back.
- **Showing and hiding a sidebar is animated** — a 200ms width transition rather than a jump. The content keeps its own width inside the collapsing panel and is clipped, so nothing squeezes together on the way out. A resize drag switches the transition off for its duration so the edge cannot lag behind the pointer, and `prefers-reduced-motion` removes it entirely.
- **A custom window title bar.** The app now draws its own 40px title bar across the top of the window instead of using the operating system's: the Emerald logo on the left, the application menu next to it, back/forward navigation, a search field, and the window's minimise / maximise / close buttons on the right. The logo/menu/navigation group and the window-controls group keep their width as the window resizes; the search field is the one flexible column and fills whatever space is left between them, shrinking first as the window narrows. It no longer disappears at any window width. Instead, once the room left for it drops below ~192px, the four menus (Edit/View/Export/Import) fold into a single menu-icon button that holds them as submenus — the fold point is measured from the menu bar's own rendered width rather than pinned to a fixed window size, since the bar itself is noticeably wider in German than in English. The window's minimum width was lowered from 900px to 720px to match, now that the bar degrades instead of clipping. Components live under `src/components/layout/titlebar/`.

  The split across platforms is deliberate rather than uniform. Windows and Linux run the window undecorated (`decorations: false`) and get HTML window buttons in Windows' 46x40 Fluent geometry plus the application menu in the bar. macOS keeps its native traffic lights (`titleBarStyle: "Overlay"`, so native fullscreen keeps working) and its native menu bar at the top of the screen, where it belongs — there the title bar only reserves room on the left for the lights. Per-platform window settings live in new `src-tauri/tauri.{windows,linux,macos}.conf.json` files, which Tauri merges over `tauri.conf.json`; `src/lib/platform.ts` makes the same distinction available to the frontend.

  The native menu is now installed on macOS only. On Windows and Linux, Tauri's `set_menu` attaches an in-window menu bar regardless of the `decorations` setting, which would have sat alongside the new one. The three Rust commands that drive the native menu (`update_menu_labels`, `set_export_menu_enabled`, `set_altar_export_menu_enabled`) already bailed out when no menu is installed, so they turn into no-ops there without any frontend branching. Both menus resolve to one implementation in the new `src/lib/menuActions.ts`, including the rules for which export items are available — so an item that is greyed out in the native macOS menu is greyed out in the HTML one under exactly the same conditions. `View > Reset View` is the one exception: it adjusts `AppShell`'s own sidebar widths, so the HTML menu re-emits the existing `reset-sidebar-widths` event rather than calling a function, and one listener answers both platforms.

  The search field is deliberately a button styled as an input, not a real text field: there is no cross-module search yet, and clicking it opens the left entry list, whose per-tab search is the search that exists today — the same thing the rail's magnifier button used to do. A real global search is a separate, later step.

  The menu bar stays visible in the Altar's distraction-free full-window mode. That mode hides the sidebars and the tab bar, but on Windows and Linux the menu is the only route to the altar's image export — exactly what that mode is usually entered for. Back/forward and the search field do hide there.

  Two known limitations on Windows: the Windows 11 Snap Layouts flyout (hovering the maximise button) is gone with an undecorated window — `Win+Arrow` and drag-to-edge snapping still work — and `Paste` in the HTML Edit menu goes through `navigator.clipboard.read()` replayed as a synthetic paste event, since `document.execCommand('paste')` is blocked in WebView2. Replaying a real event rather than inserting plain text keeps TipTap's own paste handling, including formatting and pasted images. `Ctrl+V` works natively regardless. One item did not come across: the old Windows/Linux app submenu's `About` entry has no counterpart in the HTML menu, since Settings already shows the same name and version (`Settings → About`). `Quit` is covered by the close button.
- The left sidebar's entry list can now browse Tasks, Operations, Wiki, and Altar items directly, not just Journal entries. Six tabs (**All** / Journal / Tasks / Operations / Wiki / Altar) at the top of the list switch between them; each tab has its own search, quick-create ("+"), inline rename, right-click context menu (Duplicate/Rename/Delete where applicable), and — for Journal, Operations, and Wiki — drag-and-drop linking into the editor. The new **All** tab lists every module's items together in one list, sorted by last-updated. It reuses each tab's own duplicate/delete/rename behaviour rather than a separate implementation, so it stays in sync with them; the one visible difference is that Tasks show as a plain row with a static checkbox icon instead of their usual interactive one, and only rows that can actually be dragged (Journal/Operations/Wiki) show the grab cursor.
- **Vault management moved out of Settings into its own modal**, opened from a new Vault-icon button in the left rail (directly above Settings) — the button shows the active vault's own icon once it has one. Vaults are listed as cards — clicking a card switches to that vault (the active one is disabled); Edit and Delete are inline states on the same row, sharing the same yes/no delete confirmation used elsewhere in the app (Wiki/Operations/Tasks/Altar trash). Edit changes a vault's name and its icon together — any emoji, via the shared emoji picker — in one step; a vault without one keeps the generic vault glyph, on its row and on the rail button. A new dashed "Add Vault" row at the bottom creates additional vaults directly from the modal, without going through Backup → Add Vault import.
- **A brand-new installation now goes through vault setup instead of having a vault invented for it.** The very first launch used to silently create a `default` vault named "Emerald" in the app's own directory. Now the vault list starts empty, and Emerald shows the same vault modal — without a way to dismiss it — until at least one vault exists; only the window's own title bar is shown behind it, so the window can still be moved and closed. An installation that already has a database from before multi-vault support is unaffected and still adopts it as `default`, as before.
- Opening an existing vault now takes an automatic backup of the database file (via SQLite's `VACUUM INTO`) immediately before the one-time schema-normalization migration described below runs on it.
- **A vault is now a folder you choose.** It holds `emerald.db` and an `images/` folder and nothing else, so it can be copied to another machine and opened there. The vault modal gained an **Open vault** action for exactly that: pick its `emerald.db` file and Emerald joins the vault at that file's folder — a plain folder dialog lists no files, so this is the only way to see whether a folder holds a vault before choosing it. **Add Vault** shows the folder a new vault will actually land in, updating live as its name is typed; by default that's `Documents/Emerald/{name}`, with a folder-picker button to choose somewhere else and a reset button to go back to the default.

  Deleting a vault now offers a **"Delete the files as well"** checkbox — off by default, showing the folder it would erase. Without it, only the list entry goes and the folder stays. With it, Emerald first checks the whole folder — top level and `images/` — for anything it doesn't recognise; if it finds something, it stops before touching a single file and the folder survives untouched. Only once everything in it is Emerald's own — `emerald.db`, its journal, and images it recognises — does it remove them, then the now-empty `images/` and vault folders. New vaults can now only be created in an empty folder, for the same reason. Any vault can be deleted now, including the active one and the last one remaining: deleting the active vault switches automatically to another vault, and deleting the last one returns Emerald to vault setup.

  A vault whose folder has moved or sits on a disconnected drive is marked **Folder not found**, cannot be switched to, and can be pointed at its new location. Emerald deliberately does not recreate a missing folder: SQLite would put a fresh, empty database in it and the vault would come back looking empty instead of reporting a problem. A vault Emerald is not *allowed* to read — most commonly a macOS folder under Documents, Desktop, or iCloud before access has been granted — is told apart from a genuinely missing one and marked **No access** instead, since the fix is different in each case.

  Existing installations migrate on first start. `emerald.db` and `emerald-{uuid}.db` move out of the flat application directory into `vaults/{id}/`, before anything opens them; the step is idempotent, and `vaults.json` is only rewritten once the move succeeded. It searches both `app_config_dir` and `app_data_dir`, since those are the same folder on Windows and macOS but not on Linux.
- **The tab bar can be scrolled horizontally with the mouse wheel** once it holds more open tabs than fit. It only takes over once the tabs actually overflow, and steps aside when a trackpad's own horizontal scroll is doing the work, so that isn't handled twice. Dragging a tab to reorder it still works the same as before.

### Changed
- **Both sidebars open at a width that is derived rather than picked.** The left entry list defaults to exactly the width its six tabs need (226px) instead of a round 220, and the right sidebar to the width of the whole left side — rail plus entry list, 282px — instead of an unrelated 300. Both are computed from the tab strip's own geometry, so they follow it if it changes. A width you dragged yourself is kept — the stored value is only ever written on drag-end, so an installation that never resized picks the new defaults up on its own. *View → Reset View* restores them at any time.
- **Images belong to a vault, and are served without going through the app.** They now live in `{vaultDir}/images/` instead of one directory shared by every vault, and the database stores only the filename — not an absolute path. That is what makes a vault folder portable; it also removes the path rewriting the backup importer used to need.

  Rendering no longer goes through the IPC bridge. A new `emerald-img://` URI scheme hands the bytes straight to the webview, so nothing is base64-encoded on the way and nothing is kept as a data URL in memory for the rest of the session — the two caches that used to hold every displayed image are gone. Responses are marked immutable, since the filename is a hash of the content. The altar's own image and PDF export is the one exception: it draws images onto a canvas and reads them back with `toBlob()`, which requires the source to count as the page's own origin, so export and thumbnail capture fetch each image as a data-URL instead of using the scheme — rather than depending on whether a given WebView engine honours CORS for a custom one.

  **Unused images can be cleaned up again** (Settings → Storage → *Unused images*): it reports how many images nothing points at and how much space they take, and removes exactly those. The previous automatic version had to be removed entirely because it deleted other vaults' images out of the shared directory; per-vault folders are what make the check safe. It stays a manual action, because an image inserted but not yet saved would otherwise count as unused.

  Existing images migrate with the vault: those still referenced are copied into it, and every absolute path in journal, wiki, operation and altar content is rewritten to its filename. Anything the copy missed keeps rendering from the old shared directory, which is left in place and never deleted automatically.

- **Database schema unified.** The schema previously existed only as 32 migration steps; it now also exists as a single current definition (`src/lib/schema.ts`). Fresh vaults are created from it directly, and existing vaults reach the same shape through a new migration that rebuilds their tables — this runs once, automatically, the first time a vault is opened with this version (see the automatic backup note above). A new `npm run check:schema` script keeps the two paths from silently drifting apart in future releases; it also runs the vault-image migration against seeded legacy data to confirm it rewrites the right columns and leaves the rest alone, and cross-checks six constants that exist on both the TypeScript and Rust side (image extensions, hash length, database and image folder names, the `emerald-img` scheme and its two URL forms) so the two cannot quietly drift apart.
- `.emeralddb` backups are now versioned `"3"`, reflecting that image references are filenames rather than absolute paths. Importing a backup written by a *newer* version of the app than the one doing the import is now rejected outright instead of being silently treated as understood.
- Eight foreign keys are now declared on the schema (SQLite was already enforcing them, just without a declaration): deleting an altar deletes its placements, deleting a task deletes its links, and deleting a task's parent detaches its subtasks instead of deleting them. Content in Wiki, Operations, Tasks, or Altar can no longer end up referencing a category that no longer exists.
- Deleting a Wiki, Operations, Tasks, or Altar category now moves its content to that module's default category instead of leaving it pointing at nothing. The default categories themselves can no longer be deleted, since deleting one would leave its own content stranded.
- Operations gained a third built-in category, **Other**, which is where operations go when their own category is deleted. Previously the only built-in categories were Sigils and Servitors, so a deleted category would have filed its operations under Sigils — which they are not.
- Renaming an Altar item category no longer needs to update every item in it — items now reference the category by a stable id, matching how Wiki articles and Operations already referenced theirs, rather than by the category's (renameable) name.
- Entry numbers (the `#12` shown in the link picker) are now assigned once, when an entry is created, instead of being computed from row position every time it's read. Previously, restoring a `.emeralddb` backup in Replace mode could reshuffle every entry's displayed number.
- The left icon rail lost its header: the Emerald logo, the back/forward buttons, and the search button moved into the new title bar, and the rail now starts straight in with the panel toggles. Nothing is duplicated between the two. The `.sidebar-header` CSS class went with it; `.titlebar` took its place in the two per-theme hairline rules, so the title bar and the rail's dividers still share one border colour. `--titlebar-bg` is the only new theme token — everything else in the bar reuses the existing interactive, text, menu and search tokens. The `sidebar.back` / `sidebar.forward` i18n keys moved to `titlebar.*` along with the buttons.
- The title bar's dropdowns now share the context menu's colours — both themes give `.menu-item` the same idle tone and jade hover as `.context-menu-item-default`, and the two use the same row height, so the app no longer has two differently-styled dropdowns side by side. The menu bar honours the keyboard contract its `role="menubar"` promises: Left/Right walk the bar, Down opens a menu and enters it, Up/Down move within it, Right/Left open and close a submenu, Escape closes. Opening by mouse deliberately does *not* move focus, so the Edit menu's Cut and Copy still act on the editor's selection. Both themes also gained focus rings for the window controls, menu triggers, search field and menu items — Emerald Noctis previously had no `:focus-visible` treatment at all.
- The right sidebar no longer has manually-selected tabs (Properties / Routines / Wiki / Operations / Backlinks) — there was no code path that ever switched tabs automatically, so the panel could get stuck showing content unrelated to what was open. It now always shows a single Properties panel for whatever is active, dispatched by entry type: `JournalPropertiesPanel`, `WikiPropertiesPanel`, and `OperationPropertiesPanel` (split out of the former single `OpPropertiesPanel`, which handled all three via internal branching) for Journal/Wiki/Operations, and `AltarSidebarPanel` for Altar. Sidebar components now live under `src/components/sidebar/panels/` (one panel per entry type) and `src/components/sidebar/fields/` (shared building blocks: `PropertiesReadView`/`PropertiesEditView` for the read-only vs. editable layout shell, `PropertySummaryRow` for a read-only label/value row, and `Favicon`/`Banner` for icon and cover-image upload, shared by Wiki and Operations). Each panel now renders a read-only summary while the entry is in view mode and only switches to editable form fields once the entry is opened in edit mode — previously the fields were always live-editable regardless of the entry's own edit state. The Wiki and Operations *browse* tabs were removed outright since that's already covered by the left sidebar's entry list; Routines and Backlinks were removed from the right sidebar for now (planned to return elsewhere / attached to Properties later) — their panel components (`RoutinesPanel`, `BacklinksPanel`) still exist under `sidebar/panels/` but aren't rendered anywhere currently.
- All entry actions — the edit pencil and the Save/Cancel/Delete controls — moved out of each entry view's own header and into a single action bar (`RightSidebarActionBar`) pinned above the scrollable Properties content in the right sidebar. In view mode it shows Edit (plus a Fullscreen toggle for Altar); in edit mode it shows Done, Delete (where applicable), and Cancel. A loaded Sigil operation shows no actions there, matching its existing restriction against entering edit mode. Altars gained a Delete action in the sidebar that they previously lacked. Each of the five entry views now hands its save/cancel/delete handlers to the sidebar through a new `editActions` field on `uiStore` (`setEditActions`) instead of rendering its own buttons. The bar's buttons are the shared `Button` component (`src/components/ui/Button.tsx`) in its tone-coded row-action mode — a `tone` prop (jade/amber/danger/neutral), `compact` for a 30px icon-only square matching the left sidebar's `TabIconButton`, `active` for a pressed state, and `fill` to stretch across the row; Emerald Parchment gained matching amber-tone overrides in `src/index.css` for the Edit button, which previously had no light-theme treatment.
- **The same tone-coded button styling now also covers the vault modal's row actions, the storage cleanup row, and the entry list's "+" button**, for one consistent action-button look app-wide instead of one style in the right sidebar and plain ghost/danger buttons elsewhere: the vault modal's edit/delete/save/cancel/create icon buttons (`VaultModal.tsx`), Settings → Storage's Scan (`amber`) and Delete (`danger`) buttons, and the left entry list's new-entry "+" button (`neutral`, compact).
- The right sidebar's show/hide toggle moved from a button in each entry view's header into the left icon rail, next to the entry-list toggle, so both sidebars are controlled from the same place. The per-view toggle buttons and `Dashboard`'s `onToggleRightSidebar` prop were removed. The rail's toggle icon (`PanelToggleIcon`) gained a `mirrored` variant so the two toggles read as left/right mirror images of each other.
- The left sidebar is now split into two parts: a fixed-width icon rail (logo, back/forward navigation history, search, a list collapse/expand toggle, the five module icons, and Tags/Trash/Vault/Settings at the bottom) and the entry-list panel described above, which sits next to it and can be collapsed or expanded independently. Clicking a module icon in the rail (Journal/Tasks/Operations/Wiki/Altar) switches the main view only — it no longer highlights, since it's independent of whichever tab the entry-list panel has selected.
- The sidebar's drag-resizable width now applies to the entry-list panel only; the icon rail is a fixed 56px. The saved width moved to a new `entry-list-width` localStorage key, replacing `sidebar-left-width`.
- The vault modal's footer buttons now use the shared `Button` component (jade `primary` for creating a vault, `secondary` for opening an existing one) instead of a one-off dashed, equal-weight style that existed nowhere else in the app, matching the "New X" pattern used everywhere else (New Entry, New altar, …). The create button's label changed from "Add Vault" to "New Vault" to match that convention, which reserves "Add" for items nested inside an existing list.

### Removed
- The thin jade-gradient line that used to sit above the title bar. It read as a stray visual artifact rather than an intentional accent.
- The unused `altars.aspect_ratio` and `altar_placements.scale` columns, and the empty `altar_intentions` table, have been dropped from the schema.
- The filter panel's custom-property filter row is gone along with the feature it filtered on. `FilterPanelProps` lost `propNames`, `propFilters`, `onAddPropFilter`, `onUpdatePropFilter`, and `onRemovePropFilter` — all five were still required, and all four call sites (Journal, Wiki, Operations, Tasks) had been passing empty arrays and no-op callbacks. The four i18n keys the row used (`filters.properties`, `filters.selectProperty`, `filters.valuePlaceholder`, `filters.addFilter`) had already been dropped from the locale files, so the block would have rendered raw key names had anything ever reached it. Also removed two other now-dead keys from all four locales: `altar.enterFullscreen` (its only consumer, `AltarReadingSummary`'s own fullscreen toggle, moved into the action bar) and `editor.save`.
- The active vault's card no longer shows a text "active" label next to its name; the active vault is still identified by its jade-tinted border/background and icon badge alone.
- **Custom Properties** removed entirely, including the stored data. Entries could previously carry any number of user-defined named properties (text/number/date/toggle/checkbox types) with an optional "Show in entry" read-view badge and per-property list-view filtering; none of that remains. This removes the store, the UI, the type definitions, its fields in PDF/Markdown export and the `.emerald` export/import format, `.emeralddb` backup/restore support, and Markdown-import's "unrecognised frontmatter key → custom property" behavior (unrecognised keys are now simply ignored on import). The creating migration (version 11) is gone, so fresh databases never create the `custom_properties` table, and a new migration (version 32) drops the table and its index from databases that already have it. **Any custom-property values still stored in an existing vault are deleted on first launch of this version and cannot be recovered** — they are not carried in backups taken with this release either.

### Fixed
- **The context menu could be drawn underneath the main content and looked cut off.** Both shell columns carry `position: relative; z-index: 1`, which makes them equal-ranking stacking contexts — so the menu's own very high z-index only ever applied inside the sidebar it was rendered in, and the main area, painted later, won. It is now portalled to the document body like the modal and emoji-picker overlays already were. It also clamps itself into the window instead of only flipping: a menu taller than the distance from the click to the top edge used to end up with a negative offset and lose its first entries. The altar's placed-element rows had their own hand-built copy of that menu; they use the shared one now, so the app has exactly one context-menu implementation.
- The six tabs of the left entry list ran silently past the panel edge when it was dragged narrower than they are wide. They wrap into a second row instead. While that row is wrapped the two sidebars' lower borders no longer line up — the right sidebar's action bar keeps its height rather than growing for a reason that has nothing to do with its own contents.
- Switching tabs in either sidebar nudged the whole icon row sideways by 2px: the active tab gained a 1px themed border the inactive ones did not reserve room for. Inactive tabs now hold a transparent border of the same width.
- Switching vaults left the previous vault's SQLite connection pool open. On Windows that kept the database file locked for the rest of the session, so the folder could not be moved, relocated, or deleted afterwards. `resetDbCache()` now closes the connections instead of only dropping the reference to them.
- A migration bug present since the app's early versions silently aborted after its first statement on every database, while still recording itself as applied — as a result, the default altar was never created on any vault that predates it, and some altar placements lost their reference to their altar. Opening a vault with this version repairs both: orphaned placements are reattached, and a default altar is created if none exists.
- Rows left behind in the old, retired Creations table (from before Sigils replaced it) were never included in any backup and had become invisible in the app. They are recovered into Operations as Sigils the first time a vault is opened with this version.
- Deleting a category previously left its content pointing at a category id with no matching row, rather than moving it anywhere; the 30-day trash purge did the same. Existing vaults are repaired on first open, and this can no longer happen going forward (see Changed above).
- Importing a `.emerald` file could file an article from the "Sigil Charging" Wiki category into "Other" — the list used to validate the import's category had fallen out of sync with the app's actual built-in categories.
- `.emeralddb` backup export left trashed categories out of the file while still exporting their articles, producing backups that could not be re-imported at all. Trashed categories are now included.
- The category list showed a "Category deleted" confirmation with an undo option even when the deletion had actually been rejected (e.g. attempting to delete a default category).
- Switching vaults did not reload the Tasks store, so tasks from the previous vault could still show up after switching, even though every other module's store was reloaded. `reloadAllStores()` now reloads Tasks too.
- Queued undo actions (e.g. an "item deleted" toast) are now dropped when switching vaults instead of staying queued — they close over row IDs from the vault that was just left, so executing one afterwards could silently do nothing or act on the wrong row.
- The left entry-list panel's tab icons (Journal/Tasks/Operations/Wiki/Altar) now show the same themed active/hover highlight as the right sidebar's tabs. Both sides share the same CSS classes, but the per-theme color rules for the hover state only matched the right sidebar's container, so the left tabs fell back to unstyled colors on hover in both themes. (`src/index.css`)
- Fixed a blank-screen-on-startup bug caused by an infinite render loop: entry views subscribed to the entire `uiStore` via `useUIStore()` instead of per-field selectors, and a dependency-less `useEffect` called `setEditActions` on every render, which itself triggered another render. Fixed by narrowing subscriptions to individual store fields and registering edit actions through a ref, with the effect scoped to `[isEditing]` only.
- Opening an Altar directly into edit mode while the right sidebar was closed left no Save/Cancel/Delete controls anywhere — those actions now live exclusively in the right sidebar's action bar (see Changed above), and Altar was missing from the set of view types that force the sidebar open when edit mode starts. Title edits could be silently lost as a result. `uiStore`'s `usesEditorSidebar` check now includes `'altar'`.
- The right sidebar's action bar could show or hide its Edit controls incorrectly for a loaded Sigil operation: the guard checked `is_loaded` alone, not `category_id === 'sigils'` together with it, so the check didn't match what it was documented to do. Both conditions are now required, matching `OperationSigilView`'s own edit-mode restriction. (`src/components/layout/RightSidebar.tsx`)
- Emerald Parchment: the sidebar action bar's Delete button had no hover fill and Cancel had no hover text color. Parchment's idle overrides for `.bg-red-950/30` and `.text-stone-400` outranked Tailwind's unprefixed `hover:` variants on specificity, silently swallowing the hover state. Fixed with two rules scoped to the `.sidebar-action-btn` class so other users of those utility classes are unaffected. (`src/index.css`)
- `Button`'s tone-coded row-action mode now transitions over `duration-150`, matching `.btn-primary`/`.btn-secondary`, instead of the Tailwind default transition duration.
- The right sidebar's Edit button and the read-only Properties summary rows below it lined up at visibly different widths — both the summary rows (`PropertiesReadView`, and both conditional blocks in `AltarSidebarPanel`) and the edit-mode fields (`PropertiesEditView`) added their own horizontal padding on top of the scroll container's, doubling the summary rows' inset to 24px against the action bar's 12px. The scroll container's padding is now the only horizontal inset in the right sidebar. (`src/components/layout/RightSidebar.tsx`)
- A vault's database connection could stay open — and on Windows, the file locked — even after `resetDbCache()` ran, if a `getDb()` call was still loading at that exact moment: a connection is only registered in the cache once loading finishes, so a reset that happened in between cleared the cache before that connection ever landed in it, and nothing ever closed it. `resetDbCache()` now waits for any in-flight loads before clearing. (`src/lib/db.ts`)
- Deleting a vault's files checked for foreign files only after already deleting the database and images — the check ran as a side effect of the final, non-recursive `remove_dir` calls, which fail while anything unexpected is still inside, but by then it was too late to matter. A single unrecognised file — a `desktop.ini` or `.DS_Store`, the rule rather than the exception now that vaults live under `~/Documents` — let the database and images vanish before that failure ever surfaced, leaving an empty, still-registered folder that the next `getDb()` silently repopulated with a fresh, empty database. The folder is now scanned and validated *before* anything is deleted. (`src-tauri/src/vault.rs`)
- Creating a vault whose folder could not actually be made — a name Windows rejects, a location macOS denies access to, a read-only target — still added it to the vault list, pointing at a folder that would never exist. The list entry is now rolled back when `create_vault_dirs` fails. (`src/lib/vaultManager.ts`)
- Relocating a vault to a folder already in use by another vault was not checked, unlike opening one — two vault ids resolving to the same database, where deleting one could take the other's files with it. Relocate now runs the same duplicate check as Open. (`src/components/layout/VaultModal.tsx`)
- A vault name that was a reserved Windows device name with an extension (`CON.txt`), one of the console stream names (`CONIN$`, `CONOUT$`), or long enough in bytes to exceed a filesystem's per-component limit could produce a folder name the OS refuses to create, or one truncated mid-character. `vaultFolderName()` now checks reserved names against the stem before the first dot, includes the two console streams, and caps the result at 200 UTF-8 bytes without splitting a character. (`src/lib/vaultManager.ts`)
- Export and Import menu actions could be triggered during first-run vault setup, before any vault exists — the title bar's menu stays visible throughout setup so the window can still be moved and closed.
