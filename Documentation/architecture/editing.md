# Editing

## Edit Mode Architecture

The main content area renders only the title and body. All metadata — tags, category, icon, cover image — is edited in the right sidebar's Properties panel, which writes straight to the store; the main area subscribes to the same fields.

The Properties panel is gated by `activeView.mode === 'edit'`: while viewing, each panel renders a read-only summary (`EntryReadSections`, built from collapsible `SidebarSection`s); in edit mode the same sections show editable values (`EditPropertyRow`, `PropertySelect`, `MediaPropertyRow`) — see [`components.md`](../components.md). Edit mode is entered and left only through the sidebar's action bar; there is no double-click-to-edit on the entry itself.

## Cancel: discarding new entries and reverting autosaved edits

`ActiveView.isNew` marks an entry just created by a "New" action and not yet confirmed with Done. It is session-only: `stripSessionFlags` (`src/lib/tabs.ts`) drops it before a view enters any history — restored tabs (`normalizeSavedTab`) and a tab's back/forward history (`pushHistory`, `normalizeSavedHistory`, see [Navigation History](navigation.md#navigation-history)). Otherwise a restart or Back could make Cancel treat an entry that outlived its creation session as discardable.

Cancel on a still-`isNew` entry runs the page's own Delete: the entry goes to the Trash with the usual undo toast, so nothing typed is lost outright. This holds for every entry, and for templates, blocks and languages: "New template" / "New block" / "New language" open the page with `isNew`, `useDraftPage` gets `onCancelNew` (the page's delete), and Done keeps the page. Tasks have no Cancel: Escape on a task that was just created and never named (`freshTaskIds` in `TasksView`, session-only) puts it in the Trash with Undo.

### Reverting a confirmed entry

Entries autosave the title/body shortly after typing stops, so by the time Cancel is pressed the store already holds the edited values. `useEntryEditor` (`src/hooks/useEntryEditor.ts`) therefore captures a **baseline** when edit mode is entered (`buildRestorePatch` — title, content, tags and category; every entry also has icon and cover image), and `restoreOnCancel()` writes it back together with the `updated_at` the entry had then (skipped if nothing changed), so the autosaves leave no trace in the lists.

The baseline is wider than `buildPatch` on purpose: the Properties panel saves its fields directly, so the autosave never carries them, but Cancel takes them back with the text — one rule, "Cancel restores the entry as it was when editing began". Sigils are blocks in `content`, so the same baseline covers them.

A change of category during the edit is part of it (see [Changing an entry's category](#changing-an-entrys-category)): Cancel takes the entry back to the category it had.

The baseline outlives the view: it lives in a module-level map keyed by view type and entry id (`store/entryEdit.ts`), so looking into another tab mid-edit and coming back continues the same edit. A `uiStore` subscription drops it once no tab shows the entry in edit mode (Done, Cancel, Delete, closing the tab). It is memory only; after a restart a restored edit-mode tab starts a new baseline.

## Leaving an edit

An edit ends with Done or Cancel and nothing else. Leaving a page that is being edited *and has changes* any other way asks first — save, discard, or keep editing.

`store/leaveGuardStore.ts` holds the one **guard** of the open page: a key (`guardKey(viewType, id)`), a title for the question, `isDirty()`, and `save`/`discard`, which are the page's own Done and Cancel. Entries register theirs through `useEditActions` (`guard`; dirty means the stored state differs from the baseline, an autosave is pending, or the entry is new and unconfirmed); block and template pages through `useDraftPage` (dirty means a draft exists). `confirmLeave()` raises the question — `LeaveGuardModal`, rendered once in `AppShell` — and runs the answer; Escape, the X and a click beside the modal all mean "keep editing".

What asks:

- `uiStore.setActiveView`, `navigateBack`/`navigateForward` and `closeTab` run through `whenLeaveConfirmed`: immediately when nothing is dirty, otherwise after the answer. Back/Forward step from the history *as it was before the question* (`stepGuarded`), because Save and Discard navigate themselves and would otherwise shift the step by one.
- Closing a background tab that holds changes goes through `uiStore.askInTab`: it switches to the tab, waits for its view to register its guard (`guardRegistered` — the view may have to load), asks, then closes the tab and returns to the one it was closed from.
- `resolveOpenEdits()` (`lib/openEdits.ts`) asks for every open edit in turn — the open page, then each background tab via `askInTab`. A vault switch (`vaultStore.switchVault`) and a replace or add-vault import (`useVaultImport`) call it first. `settleBeforeExit()` adds waiting for writes still under way (`drainSerialized`, `flushDrafts`) — for an update install (`StartUpdates`) and closing the window (`AppShell`, Tauri's `onCloseRequested`), after which nothing gets another chance.

What does not ask: switching to another tab (the edit continues there), and Done, Cancel and Delete themselves — `useEditActions` wraps them in `withoutLeaveGuard(key, …)`, which exempts that one page while its handler runs.

Whether a *background* tab holds changes is answered without mounting it: `holdsOpenEdit(view)` asks the **probes** registered by `draftStore` (a draft exists) and `entryEdit` (stored state differs from the baseline, the entry moved to another module, or it is new). Only such a tab is switched to; an unchanged edit-mode tab closes without a flicker.

Whoever answers "keep editing" wants to be in the entry: the Settings and Vaults windows close on that answer (`useCloseOnKeepEditing`, fed by the `stays` counter in `leaveGuardStore`), whether they asked themselves or the window's close button did. `switchVault` resolves to `false` when the user keeps editing. The add-vault import asks *before* it starts and then passes `editsResolved`, so its own switch never asks again: a second "keep editing" would leave the old vault active, and the import would fill it instead of the new one.

## Changing an entry's category

An entry has no type: which dashboards show it follows from its category and their filters (see [Where an entry opens](modules.md#where-an-entry-opens)). There is no separate "move": the category row of the properties panel (`CategoryIconCoverRows` in `EntryPropertiesPanel`) writes `category_id` through the store's `updateEntry`, inside the running edit. Nothing else is rewritten: link chips, link defaults of custom blocks and `task_links` name the entry by id with the target kind `entry` (see [Internal Links](#internal-links)), and the entry page opens any entry by id. Title, content, tags, number, icon and cover image stay as they are; a start template applies only when an entry is created (see [Starting an entry](templates.md#starting-an-entry)). The open page stays where it is — in the dashboard it was opened from — even if that dashboard no longer lists the entry.

### Cancel

Cancel writes the baseline back — title, content, tags, category, icon, cover image and `updated_at` — so a category changed during the edit comes back with the rest. `restoreOnCancel` first waits for the entry's write chain (a category change still writing is already part of the edit), then looks the baseline up by entry id (`baselineOf`). If the entry is gone by the time Cancel finishes, or a second Cancel was faster, it answers `EDIT_ENDED` and the view does nothing further.

- **No save on the way out.** While Cancel runs, the debounce, unmount and navigate-away saves are off for that entry (`isDiscarding` in `store/entryEdit.ts`, see below for the lock on the action bar); they would write the discarded text over the restored entry. The mark is per entry, not per view, and stays until the entry's next edit begins when the entry is gone.
- **The edit is locked while it writes.** `restoreOnCancel` runs inside `withEditLock` (`uiStore.ts`), which holds `uiStore.editLocked` — counted, so that overlapping holders do not release each other's lock. While it is set, `RightSidebarActionBar` disables Done, Delete and Cancel (`EditActionBar`'s `locked`); their handlers ask the store at click time, since the lock has to hold from the click that set it, not from the next paint. Leaving the page is dropped too (`whenLeaveConfirmed`): the leave question would go to the guard of the view being torn down. Closing a background tab is refused the same way (`askInTab`). Draft pages of templates and blocks pass the flag to their own bar (`LibraryPageFrame`), since the lock is global and their closing step would be dropped as well. `resolveOpenEdits` for the open page — vault switch, closing the window — does not check the lock. The automatic backup depends on the same lock: a run answers `busy` while it is set and drops what it read if `editLockEpoch()` moved meanwhile, since these writes span several tables — see [Automatic Backup](storage.md#automatic-backup).
- **Cancel waits for a pending icon.** An image icon is shrunk and stored as a file before it is written (`useShrunkIcon`), so its write can still be on the way when Cancel is pressed. The write goes through `trackEntryWrite` (`store/entryEdit.ts`); `restoreOnCancel` awaits `pendingEntryWrites` inside the lock, after `beginDiscard`, so the late write sees `isDiscarding` and drops itself instead of landing after the restore.
- **Cancel ends the edit in its own tab.** `restoreOnCancel` remembers the tab it was pressed in. If the open page is no longer that entry when the write is through — the user went to another tab meanwhile — it ends the edit there itself (`uiStore.endEditInTab`) and answers `EDIT_ENDED`, so the view neither navigates the wrong tab nor resets local state that already belongs to the next entry.
- **Merged or purged categories.** `reassignCategoriesInMemory` moves baselines off a merged or purged category (`reassignBaselineCategories`), or Cancel would fail on the foreign key.
- **A new, unconfirmed entry** is not restored: Cancel puts it in the Trash.

## Right Sidebar Action Bar

`RightSidebar.tsx` renders a `RightSidebarActionBar` pinned above the scrollable Properties content. It reads `uiStore.editActions` (set via `setEditActions`): in edit mode it shows Done/Delete/Cancel, in view mode Edit (`EditModeBar`, which a language's read view uses too). An entry a block locks (a loaded sigil, interface 6) keeps the Edit button in place, disabled, with a tooltip on a wrapper `<span>` — the locking block's reason (`EntryEffects.lockReasonKey`, the sigil's `blocks.types.sigil.locksEntry`), else `editor.lockedByBlock` — because a disabled tone `Button` takes no pointer events.

Each entry view registers its handlers through `useEditActions(active, handlers)` (`src/hooks/useEditActions.ts`):

```ts
useEditActions(isEditing, { onSave: handleDone, onCancel: handleCancel, onDelete: handleDelete });
```

The handlers live in a ref overwritten on every render, and the effect depends only on `active` (and the guard key): `setEditActions` needs to run when edit mode flips, not per keystroke, yet the handlers must see the latest `title`/`content` at call time. Calling `setEditActions` on every render, combined with a whole-store `useUIStore()` subscription, produces an infinite render loop and a blank screen — keep sidebar-consuming components on per-field selectors (see [Store Selectors](modules.md#store-selectors)).

The optional fourth handler, `flush`, is for a sidebar action that needs the *current* row rather than what the last debounced autosave wrote: the entry page passes `flushAutoSave` from `useEntryEditor`.

## List Header Portal

In list views (every module and dashboard, plus Categories, Tags, Trash and the library views Blocks, Templates and Lexicon), `Dashboard`'s header — actions, toolbar, filter panel — lives **only** in the right sidebar; there is no inline fallback above the list. `RightSidebar.tsx` hands its host `<div>` to `uiStore.listHeaderHost` through a ref callback (`setListHeaderHost`); `SidebarPortal` (`src/components/ui/SidebarPortal.tsx`) `createPortal`s its children into it whenever it is non-null. `Dashboard` renders its header through one; a library page (block, template, language — `LibraryPageFrame`) renders its sidebar content (Done/Delete/Cancel, settings, usage) through another.

Invariant: exactly one writer (the ref callback) and at most one reader at a time — `MainArea` renders one view, so only one thing portals into the host. `listHeaderHost` is a DOM node and is not persisted.

Closing the right sidebar has nothing to fall back to: the header disappears with it and the list gets the room back. `AppShell` keeps the sidebar mounted (`inert`) for the collapse animation (see [Left Sidebar](navigation.md#left-sidebar-rail--entry-list)), so the header stays visible for that stretch and vanishes once the ref callback clears `listHeaderHost`.

`RightSidebar` decides whether to offer the host from `uiStore.dashboardMounted`, not from `activeView.id`. `Dashboard` announces itself in a `useLayoutEffect` (`setDashboardMounted`) — a layout effect, so opening an entry switches the sidebar to the action bar before the first paint. Guessing from `activeView.id` gets it wrong: Tasks carries an id while showing its list (a jump target, not an open entry), and a stale id of a just-deleted entry falls back to that module's `Dashboard` — both would show the entry action bar with a meaningless Edit button. `VIEWS_WITHOUT_ENTRIES` (`dashboard`/`tags`/`categories`/`images` plus the library views) and a missing `activeView.id` also offer the host up front, so it exists before a lazily loaded list view has mounted its `Dashboard`. Categories and Tags have no entries but go through `Dashboard` so their header portals like everyone else's.

### Header contents

The props and sections are documented in [`components.md`](../components.md) (`Dashboard`, `ListToolbar`, `FilterPanel`); the rules that matter here:

- `groupBy` (`{ value, onChange, label? }`) is the grouping axis, independent of `sort` (`GroupingMode` vs. `SortMode`). A module with nothing to group omits it.
- Every dashboard's main action is `primaryAction`; `danger: true` renders the red `btn-primary-danger` (Trash). `extraActions` are compact icon buttons on the same row; `contentFooter` renders below the content in every state, for a module's second area (Blocks' built-in blocks, Templates' defaults overview, Lexicon's translate panel).
- `ListToolbar` and `FilterPanel` have only the sidebar-column presentation; `FilterPanel` is always visible. Search sits in the main area next to the title (`ListSearchField`).
- **Timeline.** `sortBlockedInTimeline` disables every non-date sort, and the grouping switch, with an explanatory tooltip — the timeline orders and groups by month on its own. The stored sort is not overwritten: the select *shows* newest first, `groupByMonth` orders by date (ascending only if the list already is), and the stored sort applies again with another layout.
- `Dashboard`'s `displayToggles` (view preferences, in the sidebar's view section, like Tasks' "Show completed") are not counted in the active-filter badge and untouched by a reset. Each `FilterList`'s "All" row clears it; "Reset filters" in the shared no-results state clears search and every filter at once.

## Auto-Save (the `useEntryEditor` hook)

Debounced auto-save (1.5 s), save-on-navigate and save-on-unmount live in `src/hooks/useEntryEditor.ts`, used by the entry page (`EntryView`). The hook takes a `buildPatch()` closure and an `update(id, patch)` action and keeps the latest closure in a ref, so the navigate-away save still reads the *previous* entry's local state (the views' load effects run after the hook's — the hook call sits above them).

The editor content is mirrored into a ref (`contentRef`) on each keystroke rather than into React state, which would re-render the whole view per keystroke. `BlockStack`'s `initialContent` (and each `TextEditor`'s) is therefore an **initial value only**. Switching entries remounts the stack via its `key` (`` `${id}:${editorEpoch}` ``), and Cancel bumps `editorEpoch` to remount from the restored baseline. Since the whole block stack serialises into one `content` string, the baseline reverts every block change of the session, sigil blocks included.

Two guards protect the save paths:

- `ready` (the view's `loadedEntryId` gate) arms the navigate/unmount saves only after local state is hydrated, so a StrictMode double-mount in edit mode cannot write empty fields.
- `src/lib/editorLock.ts` suspends all automatic editor saves while a replace/add-vault backup import runs — otherwise the unmount triggered by the import's own navigation would write the pre-import content over the restored rows.

## Internal Links

`createInternalLinkExtension(getItems)` renders linked entries as inline chips; `getItems` is ref-backed so the `[[` suggestion always sees current store state. Each chip stores `data-type="internalLink"`, `data-id`, `data-target-kind`, `data-label` and `data-icon`. Chips render identically in edit and view mode; the node view reads `editor.isEditable` at event time.

**Live lookup and gone targets.** The node view looks its target up with `useLinkTarget` (`hooks/useLinkItems.ts`) — the same `buildLinkItems` list as the picker and the sidebar, keyed once per list by `linkItemsByKey` — so icon and title follow renames, and the chip re-renders when the target is deleted or restored. The stores hold neither trashed nor purged rows, so "not in the list" is what *gone* means, without a distinction between the two. A gone chip keeps its stored `data-label`, gets `.is-gone` (dimmed, struck through, `properties.linkGoneHint` as tooltip) and dispatches no navigation. Deleting never rewrites other entries' content; restoring the target revives every chip by itself. `LinkedEntriesField`, the block link field (`LinkTarget`) and a task's link chips show the same state; `extractInternalLinks` returns each chip's decoded `label` for that, and `resolveLink` (`lib/linkItems.ts`) is the one place that builds the stand-in. A task's `task_links` row stores no title, so its chip reads "Deleted", and only while the target is in the trash: purging a task deletes the row at once (`permanentlyDeleteTask`), purging an entry leaves it to `sweepDanglingTaskLinks` on the next vault open. The PDF/HTML export marks a gone chip `il-gone` (`resolveInternalLinkIcons` → `transformInternalLinks`).

**Chip clicks.** The node view dispatches `internal-link-navigate` on `document`; one listener per open entry (`useInternalLinkNavigation`, mounted by `useTextEditorHost`) handles it, after `isValidLinkTarget`. A left click navigates in place and only in read mode. A middle click carries `detail.newTab` and opens the target with `openViewInNewTab`, in both modes — the edit stays in its own tab. The chip also calls `preventDefault()` on the middle `mousedown`, because Chromium would otherwise start autoscroll before `auxclick` fires (same trap as [tab closing](navigation.md#tabs-and-workspace-state)).

The chips in the text blocks are the record of what links where — there is no links table of their own. `block_refs` lists each chip's target per block, which is how the image cleanup and the backup find what a block names; what an open entry links is read from its in-memory text.

**What an entry links** — the "Linked entries" field (`LinkedEntriesField`) of an entry — is read straight out of the entry's text (the block stack the store holds as one string): which targets count comes from the blocks' references (`linkedIdsOf`, where a hidden block counts only if its type says so, `blockCountsLinks`), title and kind of each from its chip (`extractInternalLinks`, `src/lib/internalLinkHtml.ts`). Adding, removing and jumping to a link from the field act on the same blocks only, never on one the list passes over. Reading is deliberately `DOMParser`-free (regex over the opening `<span>` tag): it sits on the database path, where the Node check scripts run it outside a browser. Writing/remapping a chip's markup (`remapInternalLinks`) uses a real `DOMParser`, since correctness matters more there than portability.

**Sidebar ↔ editor.** The field has no reference to the open view's TipTap instance, so it talks to it through three `document`-level custom events in `lib/links.ts`: `requestEntryLinkAppend`/`requestEntryLinkReveal`/`requestEntryLinkRemove`, answered via `subscribeEntryLinkRequest` on the `BlockStack` side, which routes them to the right text block (see [Content Blocks](blocks.md#content-blocks)). A request resolves to `true` only when an editable, mounted editor accepted it via `preventDefault()`; otherwise the field falls back (e.g. `reveal` navigates to the target). `isValidLinkTarget` guards all three and the navigate-on-click handler, since the events are reachable by any script in the WebView.

**Appending** a link (from the field or the `[[` picker) always adds a full block — a horizontal rule, the target's category as an `<h3>`, then the chip — never merging into an existing block. `internalLinkBlockHtml` is the one definition of that shape, shared by the editor's `appendEntryLink` and `BlockStack`. In a completely empty entry (`isBlankContent`, regex like `extractInternalLinks`) the block goes in without its leading rule (the `separator` option) — there is no text above to separate.

Appending then jumps to and highlights the new block (`revealEntryLink` with `caretAtBlockEnd`, a frame later so the node view exists), leaving the caret at the end ready to type; revealing an existing chip selects the chip itself as a node.

**Removing** a link deletes the whole block if the chip is the sole content of an appended block (`removeEntryLink` checks for the preceding rule/heading), or just the chip if it sits inline in the user's own text. For a gone target the category is unknown, so `LinkedEntriesField` sends `headingLabels` (every category's label) and the first-block case accepts a heading with any of them. `internalLink` is an inline atom, so its parent is always a textblock.

**Cross-vault import.** A chip's `data-id` is only meaningful in its own vault. A `.emerald` file's manifest carries `links` — id, target kind and title for every chip (the live title, or for a gone target the chip's stored label) — so import can re-resolve each chip: a target that is an item of the same file points at the entry created for it (`relinkWithinFile`), any other by id first, then by the recorded title, then by the chip's own `data-label`. A chip that resolves to nothing becomes its display text (`remapInternalLinks`'s `null` case). The remap must run *before* DOMPurify: it parses and re-serialises the HTML, and that round-trip must not happen on content the sanitizer has already cleared. `sanitizeImportedHtml` is therefore the *last* step of every import that writes HTML — `.emerald` and Markdown alike.

The import also keeps the file's creation date: `importedCreatedAt` passes it to `createEntry` (`createdAt` option) so the entry sits at its place in the timeline. Only a parseable date with a four-digit year passes (dates sort as text, and `+010000-…` would sort before 2024); otherwise it falls back to now. `updated_at` is set to the same date (`importedStamp`), since an import is not an edit.

### The `.emerald` file

`.emerald` is the one file format for exchange and for the database export, written and read by `src-tauri/src/emerald_file.rs` (its module doc is the reference). Every file starts with a header in the clear, then the body:

```text
"EMRE" | version (2) | header length (u32 LE) | header JSON {kind, protection} | body
```

- `kind` says what the file holds: `items` — entries and templates for another vault (`.emerald`, this section) — or `vault` — a vault's content (`.vault.emerald`, see [DB Backup / Restore](../database.md#db-backup--restore-vaultemerald)) — or `raw` — a raw backup of a vault, which the automatic backup writes (also `.vault.emerald`, see [Raw backups](encryption.md#raw-backups)).
- `protection` is `none`, `password` (the Argon2id parameters, a 16-byte salt and a 16-byte nonce prefix) or `vaultKey` (the vault's `vault.key` as it was at export, a salt and a nonce prefix). How the two protected modes derive their key is in [Encrypted files](encryption.md#encrypted-files).

The body is a ZIP archive with exactly these members: `manifest.json` (deflated), `images/{name}` and `icons/{name}` (stored — they are compressed already); a raw backup alone also holds the vault's own `emerald.db`, `emerald.db-journal`, `vault.key` and `settings.json`, all stored (see [Raw backups](encryption.md#raw-backups)). With `none` it follows the header as it is; otherwise it is sealed in 64 KiB chunks (`emerald_seal.rs`). An older file — the bare ZIP of format 6, the JSON files before it, the envelope version 1 — is `EMERALD_OLD_FORMAT`; a header version, kind or protection this build does not know is `EMERALD_NEWER`.

The manifest is built and checked in `src/lib/emerald/manifest.ts` (pure, run by `check:blocks`): `format`, `version` (`EMERALD_FORMAT_VERSION`, 8), `kind`, and for `items` the `items` — entries (`id`, `title`, `number` for information, `createdAt`, `updatedAt`, `icon`, `cover`, `category`, `tags` by name, `blocks`) and templates (`id`, `name`, `title`, `icon`, `tags`, `blocks`; `createdAt`/`updatedAt` for information) —, `links`, `omittedImages`, `blockDefinitions`, `images` and `blockTags` (the tags the items' blocks give, by ID and name: the import finds or makes each by name as it does an item's own tags and points the blocks at it, `retagContent`). An entry's `category` is `{id, name, icon, builtin}`: its ID here and the label shown at export. A block is a row of `blocks` without owner, position and search text (`toBlockRow`), in order; `block_refs` is not in the file — the import writes the blocks through the stores, which rebuild it. The version is raised whenever an older build would import a file wrongly; Rust (`FORMAT_VERSION`) and the frontend read only this one.

`src/lib/emerald/file.ts` wraps the four commands: `writeArchive`, `openArchiveAsking` (asks for the file's own password, or for its vault's password or recovery key, through `askBackupSecret`, again after a wrong answer), `storeArchiveFiles` and `closeArchive`.

**Export** (`writeEmeraldFile(path, options)` in `src/lib/emeraldFormat.ts`, no dialog) takes the settings the export menu offers (`EmeraldExportOptions`); `exportItemsAsEmerald(options, defaultName)` asks for the path first:

- `items`: entries and templates, `{ kind, id, images? }`. The caller decides about linked entries; `linkedEntriesOf(ids, { recursive, blocked })` (blocked entries — ticked off — are listed but not followed further) lists the entries a selection links to (`block_refs`, kind `entry`), without trashed ones.
- `images`: `none` (as stored), `balanced`, `strong` (downscaled to at most 1600 / 1000 px and re-encoded on a canvas at quality 0.8 / 0.6, `lib/imageCompression.ts`) or `placeholder` (left out; listed in `omittedImages`). Each item can override it; a picture two items share gets the gentlest setting either asks for (`gentlestImageMode`).
- `protection`: `none` (the default), an own `password` — any but an empty one (`keys::check_password`) —, or `vaultKey` (an encrypted vault's only).
- `blockDefinitions` (on by default): the custom block definitions the items' copies name in their quiet `definition` note (`usedDefinitionIds`, see [Blocks](blocks.md#prefills-across-backup-and-emerald)) travel as their rows — not from the trash — with their prefilled pictures and an icon file; a prefilled link only when it points at an entry the file carries too, otherwise it is left out.

Always along, without a setting: category (with its ID) and tags by name, icons, cover, the copies of custom blocks in the content, the details of every picture the file carries that is in "Images" — name, note and tags by name, not their colour (manifest `images`, `imageDetailsOf` in `src/lib/emerald/imageDetails.ts`; a left-out picture has none) — and concealed sigils as they are, whole (they arrive concealed; the `.vault.emerald` file carries them the same way). There is no audio. A template's **Export as Emerald…** in Templates writes it with the defaults (`images: 'none'`, no protection); everything else goes through the export menu (see [The export menu](shell.md#the-export-menu)).

Pictures go from the vault into the archive in Rust, one at a time (`images::load`), so no picture crosses IPC unless it was compressed. A compressed picture keeps the hash part of its name and takes the extension of its new type; the import matches pictures by that hash (`renameStoredFiles`). The import takes the pictures of the items it creates (and the prefills of the custom blocks it adds) into "Images" with their details (`importImageDetails`): tags by name as for items (`ensureTagIds` — an existing tag keeps its colour, a new one gets a random one; with creating tags inline switched off only existing tags are matched); a picture already in "Images" — the same file, as on import into the same vault without compression — keeps a name and note it has, takes the file's where they are empty, gains the tags and comes back from the trash. Writing streams member by member into `{target}.part` beside the target (a remnant under that name is removed first, `create_new` refuses a link), flushed, and renamed into place only once the file is whole — patiently, since a scanner may hold the fresh file; a volume that refuses the flush, a network share, is no failure. The save dialog's path gets `.emerald` (or `.vault.emerald`) appended when it lacks it: the GTK dialog does not add the filter's extension.

**Import** (the import window, see [The import window](shell.md#the-import-window)). `read_emerald_file` checks the file within the limits of its kind (see [`security.md`](../security.md#emerald-import-limits)), accepts only the member shapes of its kind, checks the manifest's format, version, kind (header and manifest must agree) and item count, and returns `{ticket, kind, manifest, protected}`; the pictures stay in the file. A file of the kind `vault` or `raw` stays open in the import window as a vault's content (a raw backup's content is read from its database first). For `items` the frontend checks the manifest field by field (`itemsManifestOf` → `parseManifest`) before anything is stored; the window may then leave items out — those not ticked (`only`) and those already in the vault (`skip`, from `existingItemsOf`: the same ID, or the same title and creation date; a template by ID or name), to whose entries in-file links then point. `store_emerald_files` then stores the file's pictures and icons — all of them, also those of items left out, which the image cleanup removes later — under this vault's names and returns, per member, the name stored here (matched by the hash part of the name). The categories are resolved by the backup's rule (`resolveImportedCategories`, see [Categories are resolved](../database.md#import)): a built-in or starter category by its ID — renamed or in another language, it is the same —, every other one by the name it had at export, created when there is none of that name (a trashed namesake comes back). Every entry is created blank first so the in-file ids can be mapped; then each item's content is written: icons and pictures renamed, left-out pictures pointed at one placeholder picture stored for the import, in-file links re-pointed, other links resolved as above, `sanitizeImportedHtml` last. Last come the block definitions the imported items' copies came from, added by ID (`insertBlockDefinitions`, a definition this vault has stays as it is), usable at once at the end of the Blocks view, their prefilled pictures and icon pointed at the files stored here and a link default at the entry it names in the file (or the one already here it was skipped for). If a step fails, the entries and templates created so far are deleted again; categories, tags, definitions and picture details it created stay — a picture with details stays in "Images" —, the other pictures' files are left to the image cleanup. The ticket is closed whatever happens.

**What a chip stores.** `data-target-kind` holds the target *kind* — `entry` or `task` (`linkTargetKindOf`), never anything about the entry's category: a click opens the entry page in "All entries" (`viewOfLinkTarget` in `store/entryViews.ts`). So a change of category rewrites no chip. `linkItemKey` maps a chip and a link item onto the same key, `entry:<id>` or `task:<id>`.

## Text and Image Alignment

`TextEditor` configures `@tiptap/extension-text-align` for `heading` and `paragraph` only (`TEXT_ALIGN_TYPES`, exported from `EditorToolbar.tsx` so the extension config and the toolbar's disabled-state check share one list). Left alignment is the *absence* of the `textAlign` attribute, not an explicit `"left"`: the extension serialises whatever value it is given, and leaving it unset keeps a fresh paragraph's HTML free of a redundant attribute.

An image aligns through its own `align` attribute on the custom node in `ResizableImageExtension.tsx` — a paragraph's `text-align` never reaches it, since the image is a block node with its own width. `align` (the `Alignment` type, shared with text since the toolbar's three buttons drive both) serialises as `data-align` plus inline `margin-left`/`margin-right` (`alignMargins()`); `alignFromLegacyStyle()` reads the alignment from the margins alone for images stored without `data-align`. `data-align` is allowlisted in the `.emerald` import's DOMPurify config (`src/lib/emeraldFormat.ts`) but not in PDF export's sanitisation — nothing there reads it, and the inline margins carry the alignment regardless.
