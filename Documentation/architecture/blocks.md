# Content Blocks

## Content Blocks

Entries render their body as a vertical stack of blocks — `BlockStack` (`src/components/blocks/BlockStack.tsx`) inside `EntryDetailFrame`'s `body="scroll"`. The types are text (`core.text`, one `TextEditor` per block), fields (`core.fields`, which also carries user-built blocks), canvas and altar (`core.canvas`, `core.altar`), paint (`core.paint`) and the sigil (`core.sigil`, calculator, drawing and charge as the parts of one block).

### Stored format

Every block of an entry or a template is a row of its own in [`blocks`](../database.md#blocks), with what it points at in [`block_refs`](../database.md#block_refs). The stores load a stack from the rows in `position` order and save only the blocks that changed (`planBlockWrite` in `src/lib/blockStore.ts`): a keystroke writes its own block, a move writes one position (`lib/blocks/position.ts`), and each written block's references are rewritten (`lib/blocks/blockRefs.ts`, each type reporting its own). A row holds the block losslessly (`lib/blocks/blockRows.ts`): the instance attributes in columns of their own, every other attribute in `attrs`, the inner HTML in `html`, plain text in `text` (for a later search over the rows; the search reads the stores today).

The rows are the only record. "Images", the image cleanup and the export's linked entries ask `block_refs`; the values dashboards filter and sort by come from each type's `values` (interfaces 4/9, below). In memory the stores still hold an owner's stack as one string (`content`, what `contentOf` makes of the rows): search (each block's `searchText`), "Linked entries" and the HTML export's "Links to"/"Linked from" (its references, `linkedIdsOf`), export, templates and what the blocks conceal read that, since it is what is being typed. The format below is that string's, the one `BlockStack` hands to `useEntryEditor`, and the one `.emerald` files carry; a backup carries the rows themselves — see [`database.md`](../database.md#blocks). Each block is a top-level `<section data-block="<type>" data-block-id="<id>" …>inner HTML</section>` (`src/lib/blocks/blockHtml.ts`); the instance attributes are written in a fixed order (`orderedBlockAttrs`), then any others in theirs. Three rules carry the format:

1. Content *outside* a section is text: content with no wrapper is one text block, and raw HTML an import appends becomes another.
2. A single text block with no further attributes is written **without** a wrapper. Its ID is not in `content` then; its row keeps the one it was saved under (`blocksOfContent`).
3. Sections only appear at the top level; TipTap has no section node, so none can end up inside a text block.

`parseBlocks`/`serializeBlocks` are deliberately `DOMParser`-free, so the database path and `scripts/check-blocks.mjs` (`npm run check:blocks`, in CI) can run them under Node. `parseBlocks` finds tags with a linear scanner (`htmlTags`), not a regular expression: markup arrives from imports and other devices, and a backtracking pattern over crafted markup (thousands of `<a` without a `>`) takes minutes. Only `data-*` attributes are carried through. A block this app cannot read — an unknown type, a `data-block-v` newer than its registry entry, or damaged data — follows one rule for every type: see [Readable or not](#readable-or-not).

### Registry and interfaces

What the app has to know about a block and can do with it, the block's type says itself, through fixed interfaces (`BlockTypeDef`, `lib/blocks/blockType.ts`). Nothing about a type is wired into views, lists or categories: they ask the type and work with what comes back. Each built-in type is a file of its own under `lib/blocks/kinds/` (`text`, `fields`, `canvas` with the altar, `paint`, `sigil`); `blockTypes.ts` registers them (`registerBlockType`, the seed of a later extension API with `origin: 'plugin'`) and answers the questions about a block (`blockReadState`, `resolveBlockType`, `registeredBlockType`, `blockSearchText`, `blockStorageTag`, `blockActionsOf`, `blockSettingsOf`, `blockInstanceName`, `blockTextEditors`, `blockWithoutLink`, `blockTypePresets`, `copiedBlock`/`withDuplicatedBlock`, `entryEffects`, `upgradeBlock`); `entryProperties.ts` asks the type's `properties` itself. "Add block" and the built-in section of the Blocks view list what each type offers of itself (`presets`, `BLOCK_PRESETS` in `presets.ts`), in the order the types are registered.

Two halves, mirroring `modules.ts`/`moduleViews.ts`: `src/lib/blocks/` is pure (no React, stores or TipTap) because the database path, the checks under Node and export use it; `src/components/blocks/blockViews.ts` maps a type to its component and is imported only by `BlockStack`, since the text block pulls in TipTap; `blockSidebarViews.ts` holds a type's settings box in the block management.

**Two ground rules.** Blocks deliver values, the app builds the display: no interface returns markup or components. Where a block suggests what the user or the category can also set, the user comes before the block before the category — unless the type says its value is not to be overridden.

**General code names no block type.** Views, lists, stores, export and import ask the interfaces; none of them names a type, branches on its ID or imports a type's own module (`kinds/*`, `sigil.ts`, `sigilCalc.ts`, `canvas.ts`, `paint.ts`, `fields.ts`, `definitions.ts`, and a type's views under `components/blocks/`). An interface is added only where it serves the app in general, not to cover a single type. The places allowed to name a type are listed here, each with its reason; a new one needs a reason and the owner's consent, and the review agents report every other one. Comments may name a type as an example.

The old interface 5 (the entry's icon) is part of 3: `entryIcon` (`lib/entryIcon.ts`) asks it for lists, tabs, link chips and the export — the entry's own icon, else the block's (before the own one if not overridable), else the moon phase (until it becomes a block, #56), else the category's emoji.

**The toolkit** is what every type uses instead of building it. The pure half, `lib/blocks/toolkit.ts`: `RefReporter` (report entries, pictures, icons, tags, link chips and markup; it checks every target and drops duplicates), `linkFromSlot`/`imageFromSlot` (the link chip or the picture a slot of markup holds), `textEditorKey` (the stack's key of a block's text editor), `translatedOr` (a text written into content, with a fallback while the language is not loaded), `withoutImageInMarkup` (a block without the `<img>` tags showing a picture), `entryDate`/`blockContext` (the entry and its day — `BlockContext`, which the views get as `context` and the interfaces as `ctx`), `copiedBlockRef` (a block or part reference pointed at its copy), `readBlockSettings`/`withBlockSetting` (stored per block in `data-block-settings`; a value back at its start is not stored), `blockTypeTextKey` (a type's texts are `blocks.types.<name>.*` in the four locale files), `blockDataVersion`/`withDataVersion`. Beside it, `blockJson.ts` reads and writes a block's JSON attributes, and `blockValue.ts` reads the values blocks deliver alike everywhere (`linkValueTitle`, `compareBlockValues`). The component half, `components/blocks/toolkit.ts`: `storeBlockPicture` (a file from the disk checked, stored under its content's name and taken into "Images" with tags), `useBlockStorage` (the type's tag, made by name in a vault that lacks it), `useBlockAction` (how the view carries out an action).

**References.** `blockRefs` (`lib/blocks/blockRefs.ts`) asks the type's `refs` and adds the tags of its `properties`; it knows no block type or field kind. A block this app cannot read reports its markup's chips as links and every picture in its markup and attributes as its own (`default`, `UNREADABLE_BLOCK` through `blockInterfaces`), so "Images" never takes one out of a block that is saved unchanged. Everything that needs to know what an entry points at reads that one list: the rows of [`block_refs`](../database.md#block_refs) ("Images", the image cleanup, "include linked entries" in the export, the block tags of the lists) or, for what is being edited or exported, the same function over the content ("Linked entries" and the HTML export's "Links to"/"Linked from", `linkedIdsOf`). No export finds linked entries in the content on a way of its own; the `.emerald` file still collects every chip's title from the markup (`collectContentLinks`), since its import rewrites chips in markup, not references. `blockWithoutImage` is how "Images" takes a picture out of a place, `blockWithoutLink` how "Linked entries" removes a link no mounted text editor holds.

**Tags from blocks.** A block may give its entry tags (`properties.tags`, read from the block alone, by tag ID in its own data). They hold only while the block is there: written as references of kind `tag` on every save — only for a tag that exists, in the trash too, like the entry's own — never into `entry_tags`. The entry store reads them with the list (`readBlockTags`, `Entry.block_tags`) and takes them from each save (`BlockWrite.blockTags`); dashboard filters and the tags view count them with the entry's own (`entryTagIds`).

Where tags change, the blocks follow without the app knowing any type: `remapBlock`'s `tags` rewrites only the IDs the block's type names as its tags. A `.vault.emerald` import maps them as it maps the rows' own tags (`importTagsAndRemap`: the same ID, else the tag of the same name here). A `.emerald` file carries their names (`blockTags`, `manifestBlockTags`); its import finds or makes each tag by name as it does an item's own tags (`ensureTagIds`) and points the blocks at it (`retagContent`). A tag merging into its namesake (restoring a tag whose name was taken meanwhile) takes the blocks along (`retagBlocks`, and `retagInStores` for what is in memory); a tag deleted for good takes its references along (`dropBlockTagStatements`), and a block still naming it gives nothing. Renaming changes no ID; a tag in the trash stays given; reviving a trashed namesake keeps what the blocks give.

**Actions.** A type declares its actions; the mounted view registers how it carries one out (`useBlockAction`, through the stack's context). While editing they stand in the block's menu (the stack's and the block management's, `typeBlockActions`), followed by the type's settings — a switch as a ticked entry, a choice as one entry per option. While reading, those with `inRead` stand in a section "Actions" of the properties panel (`BlockReadActions`), one row per action and block; where several rows offer the same action, each names its block, and blocks of the same name are numbered; the session's `runAction` reaches the view.

**Copies and data versions.** Duplicating (`withDuplicatedBlock`) gives the copy a new ID and lets its type copy it; inserting a template (`instantiateTemplateBlocks`) copies every block with the map of all new IDs. A stack upgrades every block it reads (`upgradeBlock`); a block whose version is above its type's is no block of that type (`resolveBlockType`).

**What lists know of an entry's blocks.** `entryBlockSummary` (`lib/blocks/entrySummary.ts`) is everything the blocks show outside themselves, per entry, cached per content and day: what the blocks do to the entry (`effects`: the lock, what is concealed), the info line in both forms (1), what the visible blocks suggest for the properties and their rows (3, `blockSuggestions` in `entryProperties.ts`), and the values to filter and sort by (4/9, of hidden blocks too — data, not display; `entryBlockValues`, and `entryBlockValue(entry, key)`, which picks by the info line's rule: the lowest `rank`, the first among equals). It parses only content that some type's `mayContribute` lets through (`mayShowOutside` in `blockTypes.ts`); most entries are never parsed.

**The info line.** A type's `listInfo` (`ListInfoProvider`, `lib/blocks/listInfo.ts`) returns `ListInfoPart`s from `parts(block, ctx)` — a key, a rank, an icon (optional: without one the short form is the value alone), a label (a text key, or the user's own name of a field — `BlockValueLabel`), a `BlockValue` (or `null` for "holds the key, shows nothing") and the forms it appears in (`InfoForm`: `short`, `long`; both if missing). A hidden block is asked only if its type sets `evenWhenHidden`; per form and key the part with the lowest rank wins, the first among equals. The app words the parts (`blockValueText`, `lib/blockValueText.ts`): short as icon and short value (`formatIsoDateShort`, the long form as tooltip), long as `common.labelValue` ("Label: value", French with a space before the colon). A link is worded by its target's current title, looked up by ID as link chips are (`linkValueTitle` with `useLinkTitle`), the name stored with it only once the target is gone; sorting by it goes by the same title (`compareBlockValues`). The left list always shows the short form and then leaves out the category, so both dates are seen whole; a dashboard shows the form of its setting (`DashboardDisplay.info`), the entries under a tag the long one. Rows put the parts after category and date (`RowContent`'s `info`), cards on a line of their own (`CardContent`'s `info`). In a row a `text` or `link` value is cut at its end when room runs out, and gives way before the date (`.entry-list-info--free`); dates, numbers and the like never are; in a card it wraps. The fields block answers for the fields switched on for it (below); the sigil with its target date in the info line (the first loaded sigil before the others, shown for a hidden block too), as one row of the panel and as a value to filter and sort by.

**The properties panel.** It shows what the blocks add (`useEntryBlockSources`, `components/sidebar/fields/BlockSourced.tsx`): their rows after category and moon phase, reading and editing alike; a suggested icon or cover while the user has set none (a fixed one whatever they set, without a menu); the tags the blocks give after the user's, not removable there. Each is marked as the block's (`FromBlockMark` in `components/ui/`, the rail's "Blocks" icon, the block named in the tooltip). The read view's cover is the one `resolveProperty` picks.

### Readable or not

One rule for every block, in both directions between app versions, with no knowledge of any type (`blockReadState` in `blockTypes.ts`):

- **Downward — a newer app meets an older block.** A block whose data version (`data-block-v`, missing = 1) is below its type's `dataVersion` is brought up by the type's `upgrade` when a stack reads it (`upgradeBlock`). Formats of earlier 0.2.0 builds are not carried; data of 0.1.x comes only through the converter (#115).
- **Upward — an older app meets a newer block.** A block of a type this app does not know (from a newer version or an extension), or of a known type in a data version above its `dataVersion`, is `newer`. A known type whose stored data cannot be read (its `isBroken`) is `broken`.

Such a block is asked nothing of its type (`resolveBlockType` gives `undefined`). It shows only a notice — it comes from a newer version, update the app to see it; or, `broken`, it cannot be read, its data is damaged (`UnreadableBlock`, `UNREADABLE_NOTICE`) — never what it holds, since its markup may carry what its type conceals (a loaded sigil). It is not found by the search, goes into PDF, HTML and Markdown as that notice, has no actions, settings, info line, properties or effect on its entry, can only be moved, hidden or removed, and is saved byte for byte as it came; its references keep its links and pictures (`UNREADABLE_BLOCK`). An app that can read it shows it as it was. It keeps the name and icon of its registered type (`registeredBlockType`; an unknown type is "Unknown block (type)"). A block whose render throws despite all this shows the `broken` notice (`BlockErrorBoundary`).

### The block stack

**One owner for document-wide listeners.** With several text blocks, a `document`-level listener per editor would let every request hit every block, so `BlockStack` is the host of the entry's text editors ([`editors.md`](editors.md#text-editor)): toolbar, link picker, chip-click navigation, OS file drops, pointer drops from the left list and `DragGhost` exist once per entry. The stack itself handles the three `lib/links.ts` link requests: append goes to the last-focused text block, else the last; reveal/remove try each mounted text editor in order, then the first block whose references hold the link — revealed by scrolling to it, removed through its type's `withoutLink`.

**Keystrokes don't re-render the stack.** A text block's HTML goes into `blocksRef` and, serialised, to `useEntryEditor.handleContentChange`; React state only changes on structural edits (add, duplicate, remove, reorder). Read and edit mode share one tree — `Reorder.Group` stays mounted and inert in read mode — because remounting a text block on a mode switch would rebuild it from the last structural snapshot instead of the latest keystrokes. Only the grip starts a drag (`dragListener={false}`), so text selection still works.

Every block sits in a `BlockErrorBoundary`, so one that throws shows its sanitized fallback instead of taking the app down. In read mode, `BlockStack` resets when `initialContent` changes to something other than its own serialisation and reports it to the view's content mirror, so a later Done can't restore the old content.

### Instance attributes

Any block can carry `data-block-hidden="1"` (gone in read mode via CSS, so the tree stays stable; greyed out while editing), `data-block-title` (its own title) and `data-block-show-title` (`"1"`/`"0"`, overriding the type's `defaultShowTitle`). Names are in `BLOCK_ATTR` (`lib/blocks/types.ts`), rules in `lib/blocks/blockAttrs.ts`. Being part of `content`, they revert with Cancel, and a text block back at its defaults is stored without a wrapper again (`showTitleAttrValue` drops a value equal to the default).

An empty text block is hidden in read mode too (`block-frame--hidden` when `!isEditing && isTextBlockEmpty(block)`), using the same `EMPTY_TEXT_RE` check as `areBlocksEmpty` (`lib/blocks/templates.ts`). It reads the live block off `blocksRef`, since leaving edit mode can otherwise render one frame behind the just-cleared text.

### Fields block

`core.fields` (`lib/blocks/fields.ts`) is a sequence of labelled elements: text, short text, number, date, choice, yes/no, checklist, link, image, moon phase. A single field is a one-element fields block, named and iconed after it. "Add block" offers one preset per kind (`lib/blocks/presets.ts`) except `text` (the Text block covers it).

- `data-block-config` (JSON): elements and display rules (`readHideEmpty`, `readOnly`).
- `data-block-data` (JSON): scalar values by element id. Values of unknown elements are kept and written back (`orphans`).
- **Text, links and images are markup, never JSON** (`isSlotKind`): editor HTML, a real link chip or `<img src>` in a `<dd data-block-slot="el:<id>">`, so link and image pipelines see them without a special case.
- The inner HTML is also the readable fallback (a `<dl>`) for search, export and apps that don't know the type; it is rewritten on every change, while the JSON stays the truth for scalars.

`canBeEmpty(kind)` is false for yes/no, so the sidebar and builder skip "hide when empty" for it. A `text` element registers with the stack's editor registry as `<blockId>:<elementId>`, so toolbar, link requests and drops treat it like a text block; it is builder-only and has no prefill, since that would put markup into the definition.

A `link` element can carry a category filter (`linkCategories`: category IDs plus "uncategorized"), set in the builder. It lives in the element's config, so it travels with the definition, every copy and templates; no schema change. Category IDs that no longer exist (trashed, merged, purged) are ignored, and a filter left empty is no filter (`normalizeLinkCategoryFilter`). Imports (`.emerald`, merge backup) do not yet translate the IDs to the target vault's categories, so custom categories drop out of the filter there; built-in categories and "uncategorized" keep filtering, and a filter left with nothing is no filter. The link search (`LinkEditor`) then offers only entries and tasks whose category passes (`passesLinkCategoryFilter`); a link already set stays whatever its category. The filter is not editable inside an entry.

Every element carries its uses outside the block (`ElementDef.uses`, `FieldUse`): `info` (the entry's info line in lists), `panel` (a row in the properties panel), `values` (a value dashboards filter and sort by). They are the per-field settings of user-built blocks (in the sense of interface 14, but stored in the element, not through `settings`), set in the builder and in the block's sidebar with the same three icon switches (`FieldUseToggles`), and live in the element's config, so they travel with the definition, every copy, templates, backups and `.emerald`. A new field in the builder gets its kind's start values written out (`initialUses`: panel on; filter and sort on for date, number, choice, yes/no, link, short text; info line off); a single field from "Add block" starts with all three off (`NO_USES`). A use not stored is off, so nothing shows outside unasked. A picture can be used for none of them, a long text not for filtering (`canUse`). The fields block's interfaces 1, 3 and 4/9 (`kinds/fields.ts`) give the used fields in block order, keyed `field:<element ID>` — the same key in every copy of one definition — and labelled with the field's name (`BlockValueLabel.label`), or, unnamed, its kind's (`labelKey`): the short info line shows the value alone, the long one and the panel "Field: value". A long text gives its first 120 characters of plain text (none if it holds no text, only a rule or a picture), a checklist "done/all" (filtered by, not sorted by), a link its target (worded by its current title, see the info line above); of two copies in one entry an empty field ranks after a filled one (info line and values); an empty field gives no panel row.

`FieldsBlock` is controlled: each change is a new block through `onBlockChange`. In read mode, checklist items and yes/no switches can be toggled unless the block is `readOnly`, through `onPersist` → `BlockStack.persistRead`, which updates the stack (so the content mirror and the next Cancel baseline know it) and calls `onReadModeChange` — the views pass `update*(id, { content })`, since `useEntryEditor` only autosaves while editing. Nothing is written while editor saves are suspended (backup import).

Element ids may come from an import: they must match `[A-Za-z0-9_-]{1,64}` and not name an `Object.prototype` property, and `values`/`orphans`/`slots` are prototype-less — otherwise a crafted id would read a built-in property as slot HTML and crash the render.

### Sidebar block manager

The right sidebar and the main area are sibling trees, so `BlockStack` publishes its structure (on structural changes only) plus a stable API (`insert`, `duplicate`, `remove`, `reorder`, `setAttr`, `update`, `reveal`, …) to `useBlockSessionStore` (`src/store/blockSessionStore.ts`), like `uiStore.editActions`.

- The API object is created once and forwards to the latest closures through a ref, so `clear(api)` on unmount only removes that stack's own session — a remount (Cancel, entry switch) may already have replaced it. After unmount it forwards nothing, or a stale call would reach the now-open entry.
- Each mount gets a fresh `sessionId`, keying the sidebar's manager so an open menu or rename can't outlive a Cancel remount.
- Only edit mode writes: a read-mode sidebar view gets no `setAttr`, since the change would miss autosave and be swallowed by the next Cancel baseline.
- The manager's selected row lives in the store too (`selection`, tied to the `sessionId`, cleared when editing ends). A block that is added or duplicated is selected by the stack itself, its settings expanded, and the stack scrolls to it and flashes it; a new text block gets the caret without scrolling itself (`focusOnMount`), so that scroll is not cut short. Only if the right sidebar is open at that moment (`revealInSidebar: true`) does the sidebar also open its blocks section and scroll the row into view — a section collapsed on purpose is not forced open later.

The flash (`block-stack-item--revealed`) is a ring inside an `::after` of the frame: editing, on the frame's border, flush with the formatting toolbar above the stack; reading, with the edit frame's overhang, so it does not touch the content. The first visible block (`data-reveal-first`, set by `reveal`; hidden and empty blocks before it do not count) gets no top overhang, which the scroll area's top edge would cut off.

`BlockSidebarArea` (rendered by `RightSidebar` on the entry page, rows described in [components.md](../components.md)) shows the session only if its `entryId` matches the open entry. Types can add settings via `components/blocks/blockSidebarViews.ts` (read/edit variant; the fields block's and the canvas block's edit views), expanded in a box under the selected row. `blockSidebarViews.ts` must never import TipTap: the sidebar is loaded eagerly.

### Canvas block

**`core.canvas` and `core.altar` (`lib/blocks/canvas.ts`, `CanvasBlock`)**: a scene of the canvas editor in an entry. The altar is the same block with "Images" below it by default (`defaultCanvasParts`), a type of its own so that it is offered, named and iconed as one (icon `AltarIcon`, `lib/altarIcon.ts`). The built-in template `core-altar` starts an entry of the Altars category with an altar on a night background and a text block (`altarBlockSet`). The data JSON holds the artboard's size (1600 × 1000 for a new one), the elements as the canvas editor has them, the background, the guides and their lock; a picture element keeps its stored file in `ref` and `props.src`, a drawing its compact JSON, and the adapter turns a file into a URL to show and back. `storedCanvasElement` is the one place for that stored form, `storedImageElement` a picture placed new. The config JSON holds the parts the block offers (`CanvasParts`: "Images" below, shapes, text, symbols, drawing; without config, the type's defaults), set in the sidebar (`CanvasSidebarEdit`); a part switched off adds nothing new, what is on the canvas stays. Next to the parts it holds `tag`, the tag "Images" below show ('' for all; none chosen yet: the type's storage tag — an altar's is "Altar Library", `altarBlockType.storage` — see [Canvas blocks](editors.md#canvas-blocks)). The inner HTML lists the rendered picture first (`data-canvas="render"`), then each picture once (`data-canvas="image"`) and the background picture (`data-canvas="background"`), so backups, `.emerald`, exports and the image cleanup find them like any other image. A `.emerald` import that stores a picture under another name replaces that name in the scene JSON too (`renameStoredFiles` in `lib/emerald/manifest.ts`): a stored name is a hash and stands for nothing else. Every change goes into the block at once. The PNG is rendered from data URLs on Done, when the scene differs from the one editing started with (Cancel brings that one back) or the block has no render yet, and goes in through `onPersist`, only if the block still holds the scene it shows; a render per change would leave a file behind each time. The picture it replaces is removed once the entry is saved, unless something else still shows it (`discardRenders` in `imageStore.ts`). Read mode shows the scene in the canvas editor, the PDF, HTML and Markdown export the rendered picture (the type's own `export` in `kinds/canvas.ts`); a block without one is left out of them until its first Done. "Save as picture" is the type's action (`SAVE_PICTURE_ACTION`, in the block's menu and, while reading, the panel's "Actions"; offered once the canvas holds something): it opens the canvas editor's export dialog (`CanvasEditorHandle.openExport`), which renders the scene at the chosen format, area, width and background (`exportedScene`; JPEG flattened on white) and saves it through `savePictureAs` (`lib/pictureExport.ts`: the save dialog in the vault's `export/` folder (`exportDefaultPath`) under `<block type>_<yyyy-MM-dd>.<ext>` from `exportFilename` in `lib/helpers.ts`, every export's default name, then `export_image`). For "Images", a canvas's pictures are shown (role `content`), its render is the thing itself; `withoutCanvasFile` takes a picture's elements out, and the render with them until the canvas is next edited.

### Paint block

**`core.paint` (`lib/blocks/paint.ts`, `PaintBlock`)**: a drawing of its own (`parseDrawing`/`withDrawing`): the paint vector document as block data, the rendered picture and each layer's picture as `<img>` in the HTML. Its pictures are in `block_refs` as `render` and `layer` (`reportDrawing` in `kinds/paint.ts`): "Images" lists neither, and taking a picture out of a block never touches a drawing; the export shows the rendered picture. The sigil's drawing is a part of the sigil block, painted in the sigil's colours.

### Sigils

**The sigil is one block, `core.sigil` (`lib/blocks/sigil.ts`, `SigilBlock`)** with three parts: calculator, drawing and charge. Which of them it shows is the block's settings (`SIGIL_SETTINGS`, interface 14: one switch each, all on to start with; "Add block" offers only "Sigil"). A part switched off keeps what it holds, and a loaded charge stays shown whatever its switch says (`shownSigilParts`), so a sigil that acts on its entry can always be seen and unloaded. Each part has a heading of its own in the block.

**Storage.** Each part keeps its data JSON under its name in the block's data JSON, and its markup — the calculator's readable version, the drawing's pictures, the technique's link chip — in a slot of the inner HTML, `<div data-sigil-part="calc|drawing|charge">`. A part is read and written as a block of its own (`sigilPartBlock`/`withSigilPart`) under the ID `<block ID>:<part>` (`sigilPartId`) — the ID the effect locks and conceals. Slots and the technique's chip are found in linear time (the opening tag by a bounded pattern, its end by `indexOf`), since lists read them for every entry and the markup may come from an import. A block whose data JSON — its own, its calculator's or its charge's — cannot be read (`isSigilBroken`, the type's `isBroken`) is unreadable as a whole, as one from a newer app is: only the notice, never its parts (see [Readable or not](#readable-or-not)).

**The parts as building blocks.** The calculator is a building block of its own, reading and writing a block-shaped value and knowing nothing of where that sits (`lib/blocks/sigilCalc.ts`, `SigilCalc`): it always offers both ways to the letter bank, automatic and manual. The drawing is `DrawingBlock` with the sigil's colours (the paint document and its pictures: see [Paint block](#paint-block) and [Editors](editors.md#canvas-editor)); its save may finish after Done: `DrawingBlock` keeps it in the part that stays mounted, writes through `onPersist` if editing has ended, and drops the result if the stack was unmounted. The charge is `SigilCharge`. `SigilBlock` merges the parts' writes in a ref, so two writes before the next render (a drawing saved while typing in the calculator) build on each other. See also [Sigil Workflow](../database.md#sigil-workflow).

**The charge and its effect.** A charge holds `loaded`, `revealDate`, the lock scope (the whole entry, or only this sigil) and the charging technique. A loaded charge always locks and conceals the calculator and drawing of its own block, nothing else (`sigilEffect`, interface 6). `chargeConceals` is true until the reveal date — and indefinitely without one, so a charge loaded without a date stays hidden until unloaded. With the scope "whole entry" the entry cannot be edited, and the block is the one that may still write in read mode (`lockedBy`), so it can be unloaded. A block hides its own parts in its view by the part's ID (`SigilConcealed`), in both modes.

**What the other interfaces say.** The info line, the panel and the filter values carry the target date (interfaces 1, 3, 4/9): one row per sigil whose shown charge has a date (a switched-off, unloaded charge gives none), the first loaded one's date ranking before the others, also while the block is hidden. `searchText` leaves out what is concealed or switched off (`ReadContext.revealAll` reads without concealing: the stored row text in `blocks.text` holds a concealed sigil's text, since concealing depends on the day). The export delivers parts: a heading and the markup of the calculator, a heading and the drawing's picture, a heading, the target date and technique as rows and a note "loaded"/"not loaded". A switched-off part is missing in every format; a part the entry's effects conceal (`ExportContext.concealed`) is missing in PDF and Markdown and, in HTML, keeps its heading and goes out as a `concealed` part — covered, with a switch to uncover it. `refs` reports the drawing's pictures and the technique's chip even for a part that is switched off or concealed, so "Images" and the cleanup never take them out. A copy needs nothing of its own: the part IDs derive from the block's ID, so a duplicated or template-inserted loaded sigil acts on its own parts, and `duplicateEntry` keeps the content as it is. A template carries a sigil as it is.

**State and writes.** `BlockStack` folds the effects of all blocks once per structure (`entryEffects`) and passes them to every view as `effects`; lists, sidebar and menu use `entryBlockSummary` (see [Registry](#registry-and-interfaces)). Loading and unloading are read-mode writes through `onPersist`. A block concealed as a whole by another block's effect renders nothing; no type does that yet.

### User-built blocks

**Copies, without any link.** The Blocks view (`views/BlocksView.tsx`, on the rail) is a `Dashboard` of `block_definitions` rows (`blockDefinitionStore`) with a read-only "Built-in blocks" section (`BLOCK_PRESETS`) below. `{ type: 'blocks', id }` renders `BlockDefinitionEditor`, a page shaped like an entry in edit mode, its sidebar parts portalled via `SidebarPortal` (see [List Header Portal](editing.md#list-header-portal)); page shell and draft lifecycle (`LibraryPageFrame`, `useDraftPage`) are shared with [the template page](templates.md#the-dashboard-and-the-template-page). The icon is an emoji or an uploaded icon, a file of the vault's `icons/` brought down to 128px (`useShrunkIcon`); every copy carries its name and points at the same file (`block_refs`, kind `icon`). `BlockGlyph` renders either.

**Definition:** name, icon, elements and display rules (`readHideEmpty`, `readOnly`, plus `showTitle`, which becomes the instance attribute on insert). Removing a field removes it from the definition.

**Inserting** (`createFromPreset('def:<id>', …)` → `instantiateDefinition`) writes a `core.fields` block that carries everything itself — elements without `defaultValue`, display rules, name, icon (`lib/blocks/definitions.ts`) — and, in its config, the definition's ID as `definition` (`FieldsModel.definition`). That is a quiet note, not a link: nothing follows it while editing, and only the `.emerald` export reads it, to take the definition along (see [Prefills across backup and `.emerald`](#prefills-across-backup-and-emerald)). Editing or deleting the definition changes no entry and no template, and `FieldsSidebarEdit` edits a copy's settings directly.>>>>


**Prefills (`ElementDef.defaultValue`)** are what a *new* copy starts with; their stored shapes are in [`block_definitions`](../database.md#block_definitions). `slotFromDefault`/`defaultFromSlot` convert link/image defaults to and from slot HTML. `defaultsOf(elements, blockId)` turns defaults into values for a *specific* block: checklist items get fresh ids per copy. That is why `instantiateDefinition` takes a `text: FallbackText` — writing values renders the fallback. A `select` default naming a removed option is dropped on read (`parseDefault`).

**Deleting** goes straight to the Trash with Undo (`BlocksView.remove`; the draft is cleared only once the delete worked). Copies stay.

### Drafts

A block page edits a **draft**; only Done calls `updateDefinition`. The draft is mirrored into `useBlockDraftStore` (`store/draftStore.ts`, see [the template page](templates.md#the-dashboard-and-the-template-page)) rather than view state, since `MainArea` unmounts a view on module switch; the list reads it for its "Unsaved" marker.

Drafts are written along into the vault's `drafts.json` (debounced, `write_vault_drafts`), so a crash loses nothing that was typed.

- `restoreDrafts(vaultId)` reads them back when a vault opens, through the parsers a database row goes through (`parseDefinitionElements`, …); the previous vault's drafts only leave memory.
- `DRAFTS_VERSION` is 3 (language drafts, `lexicon`); a version-2 file is read as it is, a version-1 file's template tag names are mapped to ids (see [Tags](modules.md#tags)); a newer file is left untouched and nothing is written for that vault this session.
- `flushDrafts()` writes what is pending and waits — before the window closes and before an update installs, so a discarded draft doesn't return after the restart.
- A replace-mode restore calls `clearAllDrafts()` and then `flushDrafts()` (and closes every tab), or a stale draft would overwrite a freshly restored block on the next Done.

### Prefills across backup and `.emerald`

A definition's `elements` JSON is the only place a prefill's image filename or link target lives before a copy exists, so it needs its own remap: `definitionImageRefs` feeds the pictures a `.vault.emerald` and a `.emerald` file carry and the ones `collectUsedImageFilenames` protects, and `remapDefinitionDefaults` rewrites defaults on import — a `.vault.emerald` merge or replace and a `.emerald` import alike —, dropping a link default that resolves to nothing (see [`database.md`](../database.md#block_definitions)).

An entry's or template's own pictures are collected the same way in both: from the blocks (`blockRefs`) plus every stored name anywhere in a block's HTML or JSON, so a picture that only stands in a canvas background or a copy's image prefill travels along, and a block whose references cannot be read in full still keeps its pictures. A `.vault.emerald` carries every definition of the vault. A `.emerald` file of entries carries the definitions its copies name in their `definition` note (`usedDefinitionIds`, the rows by `definitionRows`; option `blockDefinitions`, on by default) — not from the trash — with their prefilled pictures and an icon file, and a prefilled link only when it points at an entry the file carries too; the import adds them by ID (`insertBlockDefinitions`, `INSERT OR IGNORE`), so a definition this vault already has — also in the Trash — stays as it is. A copy without the note brings no definition along; it still carries everything it needs itself.
